# Phase 1.3 — `tl::Variant` vs `std::variant` / `std::any`

## Summary

`tl::Variant` (`src/tl/tl/tlVariant.h`) is **not** a type-safe sum type in the
`std::variant` sense. It is a *dynamically typed value* — a tagged union with
~25 alternatives plus type-erased user objects — that is much closer to
`std::any` combined with a runtime `type` tag. It also carries a large amount of
domain behaviour that the standard types do not provide:

- implicit numeric coercions (`to_double`, `to_long`, `to_ulonglong`, …);
- ordered comparison (`operator<`) and equality across *different* alternatives,
  so it can be used as a `std::map` key (`t_array` is literally
  `std::map<tl::Variant, tl::Variant>`);
- string serialization / parsing (`to_string`, `to_parsable_string`);
- GSI integration for scripting (`t_user` / `t_user_ref` hold a
  `VariantUserClassBase *` vtable that bridges to Ruby/Python objects);
- Qt interop (`QVariant`, `QString`, `QByteArray` alternatives).

These responsibilities are intrinsic to its role as the value type of the
expression evaluator (`tlExpression`) and the scripting bridge. A drop-in
replacement with `std::variant` is therefore **not advisable**.

## Why `std::variant` does not fit the central `tl::Variant`

1. **Open alternative set.** `t_user` erases arbitrary C++ types behind
   `VariantUserClassBase`. `std::variant` requires a *closed*, compile-time list
   of alternatives. The user-object case is exactly the `std::any` use case
   (type erasure), not the `std::variant` use case.
2. **Cross-type ordering and equality.** `std::variant`'s `operator<` compares
   the *index* first, then the value. `tl::Variant` deliberately compares
   *numerically* across alternatives (`1 == 1L == 1.0`). Replacing the union
   would silently change map ordering and break persisted data.
3. **C++11 baseline.** `std::variant`/`std::any` are C++17. The default Qt5
   build still compiles at C++11 (see `klayout.pri`), and the project already
   ships hand-rolled shims for this reason (`tlOptional.h`). A core type cannot
   depend on C++17 without a guarded fallback, which would be more code than the
   current implementation.
4. **ABI / size.** The current layout is a hand-tuned `union` plus a separate
   `char *m_string`. `std::variant` would add its own discriminant and alignment
   padding to an already size-sensitive, heavily-instantiated type.

**Recommendation:** keep `tl::Variant` as-is for the dynamic-value role. The
only mechanical modernization worth doing inside it is the Phase 2.5 smart-
pointer / RAII cleanup of the manual `new`/`delete` for the `t_list`, `t_array`
and string payloads — and only behind the C++ guards, since it is in the hot
path.

## Where `std::variant` / `std::any` *do* fit (new, local code)

`std::variant` is the right tool for **closed, type-safe unions in
leaf/local code**, not for the universal value type. Concrete candidate
patterns (to apply opportunistically, guarded by `TL_CXX20` so the C++11 build
is unaffected):

| Site | Current shape | Better with |
| --- | --- | --- |
| Expression node results that are known to be one of a *fixed* small set | runtime `tl::Variant` | `std::variant<long, double, std::string>` |
| Reader/parser tokens (streamers) | `int kind; union {...}` ad-hoc | `std::variant<...>` + `std::visit` |
| Optional single value | sentinel / out-param `bool` | `std::optional` (already shimmed as `tl::optional`) |
| Truly heterogeneous one-off storage | `void *` + manual cast | `std::any` |

### Guidance for adopters

- Prefer `std::variant` when the alternative set is **fixed and known at compile
  time** and you want exhaustive `std::visit` dispatch with no `dynamic_cast`.
- Prefer `std::any` only when you genuinely need open type erasure *and* do not
  need ordering/coercion/serialization — otherwise `tl::Variant` already does
  more.
- Do **not** migrate the public `tl::Variant` API. Treat `std::variant` as a
  tool for *new* internal code paths.

## Action taken

This phase is an **assessment**; no behavioural code change is made to
`tl::Variant`. The conclusion (keep `tl::Variant`, use `std::variant` only for
new closed unions) informs later phases — in particular it scopes Phase 2.5 to
the RAII cleanup rather than a union rewrite.
