# Phase 4.4 — Coroutines for iterators (exploratory)

**Status: exploratory / low priority** (as flagged in the plan). No production
code is converted in this phase; this document records the assessment and the
recommended, guarded approach for any future trial.

## Where coroutines could help

KLayout has several hand-written iterators that are essentially state machines:

- `db::Cell` instance / shape iterators (`at_end()` style).
- Recursive cell-tree traversal (`db::RecursiveShapeIterator`,
  `db::RecursiveInstanceIterator`) — these maintain an explicit stack of
  iteration state.
- Region / Edges / EdgePairs shape collection iterators.

A coroutine generator lets such traversals be written as ordinary recursive
functions that `co_yield` each element, with the compiler synthesizing the
state machine. That removes large amounts of manual stack/cursor bookkeeping.

## Why it stays exploratory

1. **Standard generator is C++23.** `std::generator` (P2502) is only in C++23;
   on C++20 a generator type must be hand-rolled (promise type + custom
   iterator), which is exactly the boilerplate we are trying to remove.
2. **C++11 baseline.** The default Qt5 build is C++11. Any coroutine code must be
   fully guarded (`TL_HAS_GENERATOR` / `TL_CXX20`) with the existing iterator as
   the fallback — meaning two parallel implementations to maintain.
3. **Allocation / performance.** Coroutine frames may heap-allocate. The shape
   iterators are extremely hot paths; a regression here would be costly. Any
   adoption must be benchmarked against the current iterators first.
4. **ABI.** These iterators are part of widely-used public headers; switching
   their implementation type is an ABI break.

## Recommended approach (when revisited)

Prototype behind `TL_HAS_GENERATOR` (C++23) using `std::generator`, keep the
existing iterator as the default, and gate selection at compile time:

```cpp
#if TL_HAS_GENERATOR
#include <generator>

//  lazy, allocation-light only if the implementation elides the frame
std::generator<const db::Cell &> each_child (const db::Cell &c)
{
  for (auto i = c.begin_child_cells (); ! i.at_end (); ++i) {
    co_yield c.layout ()->cell (*i);
  }
}
#endif
```

Then benchmark `each_child` against the existing iterator with the
`uv`/`hyperfine` harness (see `doc/modernization/benchmarks/`) on a large
layout before considering any migration. Phase 5.3 tracks the `std::generator`
adoption itself.

## Action taken
Assessment only; no code converted. `TL_HAS_GENERATOR` is already provided by
`tlCxxFeatures.h` for the eventual prototype.
