# Phase 5.3 — `std::generator` for lazy iteration

`std::generator<T>` (C++23, P2502) is the standardized coroutine generator. A
function that `co_yield`s values becomes a lazy, single-pass range, letting the
compiler synthesize the iterator state machine that today is written by hand.

## Relationship to Phase 4.4

Phase 4.4 assessed coroutine-based iteration in general and concluded it stays
exploratory. This phase tracks the concrete vehicle for it: `std::generator`.
The two share the same target sites (the `at_end()`-style shape/instance
iterators and the recursive cell-tree traversals) and the same caveats.

## Candidate state machines to replace

- `db::RecursiveShapeIterator` / `db::RecursiveInstanceIterator`: explicit stack
  of (cell, instance, transformation) frames driving a depth-first walk. As a
  generator this is a plain recursive function with `co_yield`.
- Flat collection iterators (Region/Edges/EdgePairs) used purely for read-only
  traversal.

```cpp
#if TL_HAS_GENERATOR
tl::generator<db::Shape> shapes_in (const db::Cell &cell, unsigned int layer)
{
  for (auto s = cell.shapes (layer).begin (db::ShapeIterator::All); ! s.at_end (); ++s) {
    co_yield *s;
  }
}
#endif
```

## Availability / guard

Exposed as `tl::generator` via `tlCxxFeatures.h` behind `TL_HAS_GENERATOR`.
`<generator>` ships in GCC 14 / Clang 18 / MSVC 19.43+, so on today's default
build toolchains `TL_HAS_GENERATOR` is 0 and the alias is absent.

## Action taken
Added the guarded `tl::generator` alias. No iterators are converted: as noted in
4.4 these are hot paths with coroutine-frame allocation and ABI considerations,
so any migration must keep the existing iterator as the default and be
benchmarked first.
