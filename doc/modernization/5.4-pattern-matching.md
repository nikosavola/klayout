# Phase 5.4 — Pattern matching (C++26, proposed)

**Status: monitor only.** Pattern matching is a *proposed* C++26 feature
(P2688, "Pattern matching using `is` and `as`", and the related `inspect`
lineage). It is not in any shipping compiler, so there is nothing to guard or
implement yet. This document records why it matters to KLayout and what to watch
for.

## Why it is relevant

The two places in the code base that today do manual tag-based dispatch would
benefit most:

1. **The expression evaluator (`tlExpression`).** Evaluation branches on the
   `tl::Variant::type` tag (`t_long`, `t_double`, `t_string`, `t_list`,
   `t_user`, …) through chains of `if (v.is_double ()) … else if (v.is_long ())`.
   Pattern matching would collapse these into a single exhaustive `inspect`/
   `match` expression with compiler-checked completeness.
2. **`tl::Variant` dispatch generally** — to_string / comparison / coercion all
   switch over the same tag set.

## What to watch

- Proposal status of P2688 and successors through the C++26 cycle.
- The feature-test macro the committee assigns (likely `__cpp_pattern_matching`);
  when it lands, add a `TL_HAS_PATTERN_MATCHING` helper to `tlCxxFeatures.h`
  mirroring the existing `TL_HAS_*` entries.
- Interaction with `tl::Variant`: because `tl::Variant` is type-erased rather
  than a closed `std::variant` (see `doc/modernization/1.3-variant-evaluation.md`),
  the most natural fit is matching on the `type` enum, not structural matching
  on alternatives.

## Action taken
None (monitoring). No macro is added because there is no feature-test macro and
no compiler support to detect.
