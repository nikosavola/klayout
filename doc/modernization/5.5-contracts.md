# Phase 5.5 — Contracts (C++26, proposed)

**Status: partial — semantic markers now, language contracts later.**

C++26 contracts (P2900: function `pre(...)` / `post(...)` specifiers and
`contract_assert(...)`) are not yet available in shipping compilers. This phase
delivers the migration-guard groundwork without depending on a feature that does
not exist yet.

## What was added

`tlAssert.h` now provides two semantic markers:

```cpp
#define tl_precondition(COND)  tl_assert (COND)
#define tl_postcondition(COND) tl_assert (COND)
```

They behave exactly like `tl_assert` today (same failure handling via
`tl::assertion_failed`) but make the *intent* explicit:

```cpp
double Layout::dbu_to_um (double v) const
{
  tl_precondition (m_dbu > 0.0);     //  invariant the caller must satisfy
  double r = v * m_dbu;
  tl_postcondition (r == r);         //  not NaN
  return r;
}
```

This is useful immediately: it documents API contracts at the call/return site
and is greppable, while remaining a plain assertion under the hood.

## Migration path to real contracts

When P2900 ships and a `__cpp_contracts` feature-test macro appears:

1. Add `TL_HAS_CONTRACTS` to `tlCxxFeatures.h` alongside the other `TL_HAS_*`
   helpers.
2. Move *preconditions/postconditions* to the function **declaration** using the
   language `pre()` / `post()` specifiers — the compiler then enforces them at
   the call boundary, which a statement-level macro cannot do.
3. Re-point the in-body `tl_precondition` / `tl_postcondition` markers at
   `contract_assert(...)` (the statement-level contract form) under the guard,
   keeping `tl_assert` as the C++11/17/20/23 fallback.

Because contracts are a *declaration-level* feature, the statement macros here
cannot transparently become language contracts on their own — hence the two-step
migration above rather than a pure macro swap.

## Action taken
Added `tl_precondition` / `tl_postcondition` to `tlAssert.h` (no behavioural
change vs. `tl_assert`) and documented the path to C++26 contracts.
